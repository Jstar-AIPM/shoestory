## 二、上线过程（按真实顺序）

1. **版本号先改**：`0.1.0-stage1` → `0.2.0-v2`。理由：V1/V2 的健康检查字段一样，"部署成功"不等于"线上跑的是新代码"，版本号是最省事的判据。
2. **只部署后端**：`vefaas deploy --yes`（dependency install → release → `deploy_success`）。
   V2 后端对 V1 接口完全向后兼容（`/tasks`、`/source`、归档都没动，`/inspect` 与 `/tasks/upload` 是纯增量）→ 此刻线上仍是"输入型号"，用户侧零感知。
3. **对线上后端跑真图冒烟**：`backend/scripts/smoke_upload.py --base-url <线上后端> --admin-code …`（真图：得物商品页截图 1260×2736）。
4. **冒烟通过后再部署前端**：`vefaas deploy --yes --buildCommand "BACKEND_URL=<线上后端> npm run build && cp -r .next/static .next/standalone/.next/static" --outputPath .next/standalone`。
   注意：`rewrites` 在 **build 时**固化 `BACKEND_URL`，必须每次部署都注入（阶段 4 的坑）。
5. **浏览器 E2E 兜底**：`frontend/e2e/upload.mjs`（登录 → 上传 → 裁切框 → 体检 → 出图 → 归档 → 刷新仍在），全绿。

## 三、上线过程中发现并修掉的三个真实问题

> 这三个都是"不跑真图就不会发现"的问题 —— 正好说明为什么值得先在线上验一次。

### 问题 1：App 截图的深色界面栏被当成「鞋」
- **现象**（第一次冒烟）：CV 报 `tier=multi, count=3`，建议框给到了**底部价格栏**；视觉模型看着那个框，正确地回答
  「我看到的更像「**电商商品规格选择页**」」→ 体检这步直接断掉，连生成都没开始。
- **根因**：截图里面积最大的两个"像鞋候选"其实是顶部状态栏（暗占比 **0.988**）与底部规格/价格栏（**0.904**），真正的鞋排第三（**0.375**）。
- **修复**：新增 `is_ui_chrome()`（候选框内"暗 ≥85% 且亮 ≤15%" → 界面栏，直接剔除）；
  `_refine_subject()`：核心候选**已经像整只鞋**时不再做背景色扩张（扩张本是为修"白鞋只框到半只"，但截图里鞋的正下方紧贴规格文字，一律扩张会把界面连成一块）；
  `_background_color()` 优先用"浅色商品图区域"的中位色（截图四边都是黑栏，原来会把背景估成黑）。
- **结果**：同一张图从"建议框 = 价格栏"变成"候选只剩鞋、判定 ok、框干净地包住鞋"。

### 问题 2：质检闸门把一张**正确**的画稿判失败（白烧两次生成）
- **现象**（第二次冒烟）：画稿质检 **0.9325**、verdict `pass`、`logo_filled=1.0`（钩形确实填实）、`laces_solid_ratio=0`（鞋带没被涂黑）、`hatch_suspect=0`（无排线）—— 但任务 `failed`。
  原因：`filled_block_share=0.0149 < 0.020`（风格区间的**下限**）。
- **根因**：风格模板注释写的是"只有 `hatch_suspect` 是硬判据，其余是观察区间"，但代码把**任何**区间偏离都当不合格；
  而 V2 的填色规则恰恰是"**只填 Logo**，中底/鞋面/鞋带不得涂实" → 实心块占比本来就低，下限当闸门与产品规则直接冲突。
- **修复**：`QualityGate` 新增 `style_hard_keys` / `style_hard_max`，把"风格偏离"拆成 `style_ok`（全部偏离，报告用）与 `style_blocked`（只有硬闸门内才决定成败）。
  硬闸门 = **排线** + **大面积涂黑上限 0.100**；"Logo 到底填没填实"交给语义闸门 `logo_filled ≥ 0.6`，比像素占比更准。
  失败文案也按路径给：上传图没有"候选图"可换，改为"换一张更清晰的正侧面图重传"。
- **结果**：同一张画稿（同样的实测数值）现在判**合格**，任务一次达标。

### 问题 3（部署前就修了，一并记录）：上传接口的坐标系
- 服务端会把长边 >2400 的图缩小、并按 EXIF 方向摆正，但客户端的裁切框是"客户端那张图"的坐标系。
  不换算 → **不报错，只是裁到鞋以外**。已在部署前修好并加了 12 项测试（含"还原修复必失败"的反向验证）。
  线上自检：`/inspect` 报的尺寸 == 摆正后的真实尺寸 ✅（1260×2736，服务端确实缩过图）。

# 第二轮产品反馈（2026-09-23 晚）· 改名、交互修复、以及"规则为什么误杀"

> 产品经理上传了 AJ36 与 Air Force 1 两张**高质量**截图，两张都没能出图。
> 我从线上对象存储里把任务记录全部拉出来做了数据定位，结论写在下面 —— 不是模型不行，是**规则太刚 + 失败就 dead-end**。

## 一、真因（线上数据，不是猜测）

| 图 | 线上表现 | 根因 |
| --- | --- | --- |
| **AJ36**（重画 2 次） | 2 次重画后 `failed`，用户连图都看不到 | 照片那个角度**看不到飞人 Logo**，模型于是编了个装饰性 ∞ 符号；判官正确地判"Logo 不对"（`logo_legibility=0.35`、`logo_filled=0.0`）→ 两个硬闸门不过 → 整单失败 |
| **Air Force 1** | 没有生成任务记录（卡在体检前） | 商品页截图里**同一双鞋重复出现多张**，CV 判 `multi`（"这张图里有好几双鞋"）→ 用户一框大就更容易被判"框里不止一双" → 走不下去 |
| 两张共同的体验问题 | 失败文案写着"已把最接近的一张交给您裁决"，但界面**根本没显示那张图** | 失败即 dead-end，与文案自相矛盾 |

## 二、规则怎么改（"对效果的把控"这块的答案）

原来的硬闸门混了两种性质完全不同的检查，现在把它们分开：

| 类型 | 检查项 | 现在的处理 |
| --- | --- | --- |
| **确定性可判**（继续当硬闸门） | 画布 3:2 / 纯二值 / 白底；排线（hatch）；整块涂黑上限 | 不过 → 自动重画一次；仍不过 → 交付最接近的一张 |
| **语义判断**（降为软性） | Logo 填实（`logo_filled`）、鞋带实心（`laces_solid_ratio`）、文字可辨（`text_legible`） | 只影响"要不要自动重画"，**绝不再阻止交付** |
| **Logo 是否该画** | —— | **以原图里看得见的为准**：看得见才要求填实、且只画那一处；看不见就明确禁止编造（判官同样按此判定，看不见标识时该项给 1.0） |
| **多主体判定** | CV 判"框里不止一双" | **先问视觉模型**：它认出只有一双 → 放行（只给软提示）；它也认为不止一双才要求重新框选 |
| **永不 dead-end** | —— | 只要画出了至少一张，一律进入"效果确认"交给用户裁决；只有一张都没画出来（上游报错/预算超限）才是 `failed` |
